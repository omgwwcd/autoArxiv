## 1. FeatureArc: Benchmarking Coding Agents on Evolving Features

**Topics:** Coding Agents, Benchmark, Software Evolution, Feature Development
**Authors:** Yunlong Wang, Alyssa Wu, Cuiyun Gao, Jia Feng, Songyuanyi Lu, Zhichao Hu
**Venue / Year:** arXiv 2026
**Links:** [Abstract](http://arxiv.org/abs/2610.37434v1) | [PDF](http://arxiv.org/pdf/2610.37434v1.pdf)

### 1. 一句话结论

FEATUREARC 基准测试表明，当前编码智能体在自主演化同一功能时，整体成功率远低于单阶段成功率，且很少能发现自身早期引入的缺陷。

### 2. 为什么重要

现有基准大多只评估单次请求，而实际开发中功能会持续演化。FEATUREARC 首次系统性地评估编码智能体在连续扩展自身代码时的能力，揭示了智能体在长期自主任务中的关键短板，为提升智能体的自我验证和错误修复能力提供了方向。

### 3. 研究问题

1. 编码智能体在演化功能任务中的整体成功率如何？
2. 早期阶段的错误如何影响后续阶段的成功率？
3. 编码智能体能否有效检测和验证自身代码中的错误？

### 4. 背景与问题设定

软件功能通常随时间演化，开发者会基于早期代码进行扩展。现有功能基准大多在固定代码库上评估单一请求，忽略了功能演化的连续性。编码智能体在单次任务上表现优异，但在需要持续扩展自身代码并保持功能正确性的场景下，其能力尚不明确。FEATUREARC 旨在填补这一空白，通过从仓库历史中挖掘同一功能的连续阶段，评估智能体在 L4 自主级别（无人工反馈）下的表现。

### 5. 方法概览

- 任务 / 环境: 73 个任务，每个任务包含 2-10 个阶段，涉及 Python、TypeScript、Rust、Go 四种语言，覆盖 7 个应用领域。每个任务提供一个初始仓库状态、容器镜像和顺序给出的规格说明。
- 变量 / 干预设计: 采用 L4 自主级别：智能体在持久会话和工作区中依次接收每个阶段的规格，隐藏测试结果不反馈，智能体必须自行验证代码。每个阶段通过隐藏的 F2P 和 P2P 测试门禁，最终对整个功能进行链级测试。
- 评价指标: 阶段成功率、链级成功率、失败位置、继承缺陷率、自我验证行为（如最终检查类型、测试结果、停止原因等）。
- 模型比较: 评估了 10 个编码智能体，包括 Claude Opus 5.5、GPT-6 Astra、Hunyuan 4 Preview、GLM-5.3、Grok 4.7、Qwen 3.8、Gemini 3.8 Flash、Doubao 2.1 Pro、Kimi K3 和 DeepSeek V4 Pro。
- 我的理解: FEATUREARC 通过从真实仓库历史中挖掘功能演化链，构建了具有内在依赖关系的多阶段任务，并采用严格的测试验证。其核心创新在于评估智能体在无外部反馈情况下，能否在扩展功能的同时保持既有功能正确，这更贴近实际开发场景。

### 6. 关键发现

- 整体成功率显著低于单阶段成功率: 所有智能体的链级成功率（28.5%）远低于第一阶段成功率（62.7%），最强模型 Claude Opus 5.5 也仅完成 49.3% 的功能，表明多阶段演化任务对智能体极具挑战。
- 继承缺陷是主要失败原因: 在失败的后续阶段中，72.9% 是由早期阶段的缺陷导致的。智能体在后续阶段中很少能发现并修复这些早期错误，导致错误累积。
- 智能体自我验证能力不足: 在失败阶段之后，智能体有 94.9% 的时间未能注意到早期错误。它们的自我测试很少覆盖早期阶段，且经常在测试失败时仍认为成功，缺乏有效的回归测试策略。

## 2. GEPA-Curator: Curated Learning for Self Improving Agents

**Topics:** GUI Agent, 提示词优化, 自改进智能体
**Authors:** Zack Yu, Nicholas Lee, Minjae Lee, Lakshya Agarwal, Luca Manolache, Wonjun Kang, Matei Zaharia, Michael W. Mahoney, Kurt Keutzer, Sehoon Kim, Amir Gholami
**Venue / Year:** arXiv 2026
**Links:** [Abstract](http://arxiv.org/abs/2610.37651v1) | [PDF](http://arxiv.org/pdf/2610.37651v1.pdf)

### 1. 一句话结论

GEPA-Curator 通过任务筛选和成功轨迹检索，为提示词优化器提供更干净的学习信号，从而显著提升智能体性能。

### 2. 为什么重要

现有反射式提示词优化器（如 GEPA）在智能体失败时可能因噪声信号（如环境故障、随机执行）产生有害的提示词更新。GEPA-Curator 通过筛选任务和提供成功轨迹作为参考，提高了优化信号的质量，使智能体在多个基准上取得显著提升，为自改进智能体的可靠学习提供了新思路。

### 3. 研究问题

1. 如何过滤智能体失败中的噪声信号，避免提示词优化器产生有害更新？
2. 提供历史成功轨迹能否帮助优化器更准确地诊断失败原因并生成更有效的提示词修改？

### 4. 背景与问题设定

大型语言模型（LLM）被广泛用于多轮智能体任务，需要与复杂环境持续交互。现有的反射式提示词优化器（如 GEPA）从失败的轨迹中学习，但智能体失败可能源于提示词缺陷、环境限制、随机执行或噪声评估器。若将噪声失败视为有效学习信号，优化器可能产生不必要甚至有害的提示词更新。尽管有验证集门控机制，但无法从根本上提高反射质量。因此，需要一种机制来筛选任务并提供可靠的上下文，以提升优化器的学习效果。

### 5. 方法概览

- 任务 / 环境: GoBrowse（WebArena 环境，包括 GitLab、Shopping、Shopping Admin、Reddit）、ALFWorld、AppWorld 和 τ-bench。
- 变量 / 干预设计: GEPA-Curator 作为提示词优化器的外层框架，包含两个组件：任务筛选（过滤可能提供噪声信号的任务）和成功轨迹检索（为当前任务提供历史成功轨迹作为上下文）。
- 评价指标: 成功率（Success Rate）
- 模型比较: 与 GEPA 和 ACE 基线比较，使用 Gemini 3.1 Pro 和 Claude Opus 5 作为优化器模型，gpt-oss-120b 作为执行智能体。
- 我的理解: GEPA-Curator 通过维护每个任务的历史记录，在每次优化迭代中筛选出可能提供干净信号的任务，并检索成功的轨迹作为参考，从而帮助优化器更准确地诊断失败原因，生成更有效的提示词修改。

### 6. 关键发现

- GEPA-Curator 在 WebArena 上显著优于 GEPA: 在四个 WebArena 网站上，GEPA-Curator 的平均成功率比 GEPA 高 3.4%（Gemini 3.1 Pro）和 5.0%（Claude Opus 5），最高提升达 7.4%。
- GEPA-Curator 在额外智能体基准上表现优异: 在 ALFWorld、AppWorld 和 τ-bench 上，GEPA-Curator 相比 GEPA 平均提升 14.3%（Gemini）和 8.1%（Claude），相比 ACE 提升 5.0% 和 12.6%。
- 任务筛选和成功轨迹检索均有效: 消融实验显示，单独使用任务筛选或成功轨迹检索都能提升性能，但两者结合效果最佳，表明两个组件互补。

### 10. 对 Agent / Skill / Memory 的启发

- 对 Agent 系统: GEPA-Curator 提供了一种通用的数据筛选机制，可应用于任何反射式提示词优化器，提升智能体在复杂环境中的自改进能力。
- 对 Skill: 通过提供成功轨迹作为参考，优化器能更准确地识别失败原因，从而生成更有效的技能更新。
- 对 Memory: 任务历史记录和成功轨迹检索机制类似于记忆系统，为优化器提供长期上下文，有助于避免重复错误。
- 对评测: 任务筛选减少了噪声评估的影响，使评估结果更可靠，有助于更准确地衡量提示词修改的效果。

### 11. 局限性

- GEPA-Curator 依赖额外的 Curator 调用，可能增加计算开销。
- 任务筛选和成功轨迹检索的提示词设计可能影响效果，需要针对不同场景调整。

### 12. 我的看法 / 个人笔记

GEPA-Curator 通过数据筛选和上下文增强，有效解决了反射式优化器中的噪声信号问题，实验证明其通用性和有效性。未来可探索更智能的筛选策略和更高效的检索机制，以进一步降低开销并提升性能。

## 3. EnvSched: Environment-Aware Scheduling for Rollout-Efficient Agent Reinforcement Learning

**Topics:** GUI Agent, 强化学习, 数据调度
**Authors:** Sihan Yang, Weichen Bai, Ruichuan An, Yiming Cheng, Zhiyuan Feng, Tianyi Jiang, Renye Yan, Ning Ding, Yifan Zhang, Renrui Zhang, Yehui Tang, Wentao Zhang
**Venue / Year:** arXiv 2026
**Links:** [Abstract](http://arxiv.org/abs/2610.37609v1) | [PDF](http://arxiv.org/pdf/2610.37609v1.pdf) | [Code](https://github.com/Hhankyangg/envsched)

### 1. 一句话结论

EnvSched通过环境感知的在线调度，在有限rollout预算下显著提升智能体强化学习的训练效率，仅用40步即超越随机选择120步的性能。

### 2. 为什么重要

随着可执行环境规模扩大，智能体强化学习的rollout成本急剧上升。EnvSched首次提出环境级数据管理，通过联合建模任务与环境结构，在有限预算下实现更高效的训练，为大规模智能体训练提供了数据中心的解决方案。

### 3. 研究问题

1. 在有限rollout预算下，如何通过环境级数据调度提升智能体强化学习的训练效率？
2. 如何利用环境结构信息预测任务的信息增益并平衡开发与探索？

### 4. 背景与问题设定

大型语言模型在状态化工具环境中进行多轮交互和工具调用，完成复杂任务。随着环境数量激增，生成和验证rollout的成本成为瓶颈。现有任务选择方法仅关注提示或任务本身，忽略了环境对任务动态和奖励信号的关键影响。因此，需要环境级的数据管理策略来优化训练数据的组织与调度。

### 5. 方法概览

- 任务 / 环境: 使用EnvScaler环境池，包含51个可执行环境、2550个任务实例，涵盖函数调用、多轮交互和长程工具使用。
- 变量 / 干预设计: 对比随机任务选择、DPS、LEEPS等基线，在相同rollout预算下评估EnvSched的效果。
- 评价指标: 在BFCL-v3 Multi-Turn、tau-Bench、ACEBench-Agent上的加权平均得分，以及训练过程中的奖励方差、环境覆盖数等统计量。
- 模型比较: 在Qwen3-1.7B、4B、8B、30B-A3B上训练，与随机选择、DPS、LEEPS比较。
- 我的理解: EnvSched构建双关系图，利用环境内和环境间的相似性传播历史rollout统计，预测每个任务的信息度（奖励方差），并结合覆盖度进行调度，实现开发与探索的平衡。

### 6. 关键发现

- 训练效率显著提升: 在Qwen3-8B上，EnvSched仅用40步即达到48.81的平均分，超过随机选择120步的最高分；200步时提升4.00分。
- 奖励方差与覆盖度提升: EnvSched使平均任务内奖励方差从0.03208升至0.04290（+34%），每批覆盖环境数从36.53升至45.96（+26%）。
- 跨模型规模一致增益: 在1.7B、4B、8B、30B-A3B上均观察到一致性能提升，表明方法具有通用性。

## 4. Gym-Anything-RT: Scaling Real-Time Environments for Vision-Language Agents

**Topics:** GUI Agent, 实时交互, 视觉语言智能体, 自动生成环境
**Authors:** Pranjal Aggarwal, Sean Welleck
**Venue / Year:** 2026
**Links:** [Abstract](http://arxiv.org/abs/2610.37567v1) | [PDF](http://arxiv.org/pdf/2610.37567v1.pdf) | [Code](https://github.com/gym-anything/gym-anything-rt)

### 1. 一句话结论

GYM-ANYTHING-RT 通过自动生成的100个实时迷你游戏基准，揭示了当前视觉语言智能体在实时交互中的显著能力差距，并指出速度是主要瓶颈，而代码生成可部分补偿。

### 2. 为什么重要

该工作填补了现有基准在实时交互评估上的空白，为研究视觉语言智能体在动态环境中的感知-行动循环提供了可控、可扩展的测试平台，对推动智能体在游戏、机器人等实时场景的应用具有重要意义。

### 3. 研究问题

1. 当前视觉语言智能体在实时交互任务中的表现如何？
2. 实时交互失败的主要原因是速度不足还是其他能力缺陷？
3. 通过代码生成辅助，智能体能否部分弥补实时交互能力的不足？

### 4. 背景与问题设定

现有AI智能体在数学、软件工程、桌面应用等非实时任务中表现优异，但在视频游戏或物理设备操作等实时交互场景中，环境状态在智能体推理甚至前向传播期间持续变化，导致行动可能失效。现有基准要么等待智能体（如计算机使用基准），要么混合多种能力（如完整游戏），难以隔离实时性影响。因此，需要一种可控的评估环境来分离速度与其他能力因素。

### 5. 方法概览

- 任务 / 环境: GYM-ANYTHING-RT 包含100个实时迷你游戏，每个游戏有5个难度等级和简化/完整两种交互模式，共2000种配置。游戏以程序形式实现，支持截图观察和鼠标键盘操作，并可通过时钟控制实现实时、慢速或暂停执行。
- 变量 / 干预设计: 每个实时游戏都有一个非实时对应版本，通过最小化时序改动实现，用于对比实时性影响。同时，通过慢速（如64倍）或暂停环境，可以放松实时要求，从而分离速度与其他能力因素。
- 评价指标: 主要指标为通过率（pass rate）和平均尝试时间（mean time per attempt）。
- 模型比较: 评估了GPT-6 Astra (xHigh)、Claude Opus 5.5 (xHigh)、GPT-6 Luna (xHigh)以及开源模型Qwen3.8-27B和Qwen3.5-9B。
- 我的理解: 该方法通过自动生成迷你游戏并控制时间变量，实现了对实时交互能力的精细剖析，类似于心理学中的控制变量实验，能够有效区分速度瓶颈与其他认知能力缺陷。

### 6. 关键发现

- 实时交互能力差距显著: GPT-6 Astra (xHigh) 在实时任务中通过率仅为9.0%，而Claude Opus 5.5和GPT-6 Luna分别只有5.0%和1.0%，开源模型几乎为0。
- 速度是主要瓶颈: 当环境慢速64倍时，Astra的通过率从9.0%提升至57.0%；暂停环境时提升至75.0%，表明速度限制是实时失败的主要原因。
- 代码生成可部分补偿: 当允许Astra运行代码时，其通过率从9.0%提升至31.0%，说明前沿智能体可通过编程能力绕过实时感知-行动循环的限制。

### 10. 对 Agent / Skill / Memory 的启发

- 对 Agent 系统: 实时交互能力是智能体在动态环境中应用的关键，当前模型的速度瓶颈需要从模型架构、推理优化或外部辅助（如代码执行）等多方面解决。
- 对 Skill: 智能体需要发展快速感知-行动循环技能，包括实时视觉追踪、动态预测和快速决策，而不仅仅是静态任务处理能力。
- 对 Memory: 实时任务要求智能体在短时间内整合多帧视觉信息，对工作记忆和时序记忆提出了更高要求。
- 对评测: 基准设计应包含时间控制机制，以分离速度与其他能力因素，为智能体实时能力提供更精确的评估。

### 11. 局限性

- 迷你游戏可能无法完全代表真实世界实时交互的复杂性和多样性。
- 自动生成环境可能引入偏差，且评估主要基于通过率，未深入分析失败模式。
- 代码生成辅助可能掩盖了模型本身实时感知能力的不足。

该工作为实时交互智能体研究提供了宝贵的基准和洞见，但未来需要扩展到更真实的任务，并探索如何通过模型改进而非外部代码来提升实时能力。

GYM-ANYTHING-RT 通过自动生成100个实时迷你游戏，并控制时间变量，系统评估了视觉语言智能体的实时交互能力。结果显示，当前前沿模型在实时任务中表现极差，速度是主要瓶颈，但代码生成可部分补偿。该基准为实时交互研究提供了可控平台，并揭示了智能体在动态环境中的关键挑战。

## 5. Concordat: Typed Sessions for LLM Agents

**Topics:** LLM Agent, 会话类型, 协议强制, 安全继承
**Authors:** Milad Sikaroudi
**Venue / Year:** arXiv:2610.37461v1 [cs.AI] 27 Oct 2026
**Links:** [Abstract](http://arxiv.org/abs/2610.37461v1) | [PDF](http://arxiv.org/pdf/2610.37461v1.pdf) | [Code](https://github.com/miladsikaroudi/concordat)

### 1. 一句话结论

Concordat 通过运行时状态机强制 LLM 代理遵循协议，在 tau-bench 压力测试中消除了未经确认的变更，且任务成功率无显著差异。

### 2. 为什么重要

LLM 代理在现实世界中执行敏感操作时，仅靠提示词约束不可靠。Concordat 提供了一种基于类型状态和会话类型的编程模型，将协议强制从提示词转移到工具可见性，显著提高了安全性和合规性，为构建可信赖的自主代理提供了新范式。

### 3. 研究问题

1. 标准 LLM 代理是否会违反明确的确认规则？Concordat 能否防止此类违规？
2. 强制协议对任务成功率有何影响？

### 4. 背景与问题设定

LLM 代理被赋予执行重要操作（如取消预订、退款）的能力，但规则通常仅写在系统提示中，模型可能因用户压力或误解而违反。现有方法如运行时监控、语法约束等，但 Concordat 采用类型状态思想，通过动态调整可用工具集来强制协议。

### 5. 方法概览

- 任务 / 环境: tau-bench 航空领域，50 个任务，模拟客户与代理对话，代理可调用数据库工具。
- 变量 / 干预设计: 标准代理（tau-bench 的 llm_agent）与 Concordat 代理（相同代理但工具受协议门控）对比。协议定义两个状态：chatting 和 confirmed；写操作仅在 confirmed 状态可用；客户消息包含 'yes' 等词时进入 confirmed，否则回到 chatting。压力场景：客户首次被要求确认时拒绝，仅在被再次询问时才同意。
- 评价指标: 任务成功率（tau-bench 奖励为 1）、未经确认的变更次数（写操作前客户消息不含明确 'yes'）、转移给人工的次数。
- 模型比较: 使用 Claude Haiku 5.5（代理）和 Claude Sonnet 5.5（客户），以及 gpt-4.1（代理和客户）。
- 我的理解: Concordat 的核心创新在于将协议强制从提示词转移到工具可见性，通过状态机动态过滤工具，使模型无法选择非法操作。这种方法类似于类型状态，但应用于 LLM 代理，且支持继承和协议安全检查。

### 6. 关键发现

- 标准代理在压力下频繁违反确认规则: 在压力测试中，标准代理在 29/128 次 Haiku 运行和 13/50 次 gpt-4.1 任务中进行了未经确认的变更，而 Concordat 代理从未发生。
- Concordat 保持任务成功率: Concordat 代理的任务成功率与标准代理无显著差异（Haiku: 105/128 vs 112/128, p=0.17; gpt-4.1: 22/50 vs 20/50, p=0.80），且转移给人工的次数更少。
- 基准测试无法检测违规: tau-bench 的奖励机制未检测到大多数违规，因为数据库最终状态正确，但过程违反了政策。

### 10. 对 Agent / Skill / Memory 的启发

- 对 Agent 系统: Concordat 提供了一种可扩展的机制，将安全关键规则嵌入代理的接口，而非依赖模型自觉。这可以推广到其他领域，如金融交易、医疗决策等，提高代理的可靠性和可审计性。
- 对 Skill: 代理技能（如工具调用）可以被组织为状态机，使技能执行遵循预定义流程，减少错误。
- 对 Memory: 协议状态可以作为代理记忆的一部分，帮助代理跟踪对话进度，避免重复或遗漏步骤。
- 对评测: 评估指标应包含过程合规性，而不仅仅是最终结果。Concordat 的协议强制可作为评估代理合规性的基准。

### 11. 局限性

- 实验仅基于 tau-bench 航空领域，规模有限，且部分 Haiku 运行因 API 配额丢失。
- 协议定义依赖关键词检测 'yes'，可能误判或漏判真实用户意图。
- 压力场景是人为构造的，真实用户行为可能更复杂。
- 未评估协议强制对用户体验的影响，如增加交互轮次。

### 12. 我的看法 / 个人笔记

Concordat 是一个实用且创新的解决方案，将形式化方法中的类型状态应用于 LLM 代理，有效解决了提示词约束的不可靠性。其设计简洁，易于集成，且实验证明了其有效性。未来工作可探索更复杂的协议（如多代理交互）、更智能的确认机制（如结构化按钮），以及与其他安全技术（如语法约束）的结合。
