## 1. Beyond Fault Localization: A Trajectory-Level Study of LLM Agents for Microservice Root Cause Analysis

**Topics:** LLM Agent, Root Cause Analysis, Microservices, Diagnostic Trajectory
**Authors:** Qisheng Lu, Aoyang Fang, Junjielong Xu, Jin'ao Shang, Songhan Zhang, Yifan Yang, Xiaochuan Yan, Pinjia He
**Venue / Year:** arXiv 2026
**Links:** [Abstract](http://arxiv.org/abs/2608.21310v1) | [PDF](http://arxiv.org/pdf/2608.21310v1.pdf)

### 1. 一句话结论

Trajectory-level evaluation reveals that LLM agents for microservice root cause analysis often localize the correct service but fail to reconstruct the fault propagation path, and a two-stage defense (DiagGuard) improves accuracy from 43.5% to 52.5%.

### 2. 为什么重要

Current RCA evaluations only check final answer correctness, ignoring the diagnostic process. This work shows that process-level failures (e.g., evidence omission, misinterpretation) are common and can be systematically addressed, leading to more trustworthy automated diagnosis.

### 3. 研究问题

1. What separates a sound diagnostic process from a failing one in LLM-based RCA?
2. Can mined failure modes be operationalized into a defense that improves RCA performance?

### 4. 背景与问题设定

Microservice root cause analysis (RCA) is typically evaluated by endpoint correctness (e.g., Acc@k), which does not reveal the evidentiary basis or fault propagation route. LLM agents now perform RCA via multi-step telemetry queries, producing observable trajectories. However, no process-level ground truth exists to evaluate these trajectories against. This paper introduces manually annotated service-level fault propagation paths and a trajectory-level framework to characterize agent behavior.

### 5. 方法概览

- 任务 / 环境: Microservice RCA benchmarks: RCABench (500 cases sampled from 1,430) and AIOps 2025 (400 incidents). Agents query telemetry (SQL) over a shared store to diagnose root cause and propagation path.
- 变量 / 干预设计: Six agent frameworks (THINKDEPTH.AI, AIQ, TASKWEAVER, CLAUDECODE, OPENRCA, MABC) under shared backbone Qwen; one framework rerun on Claude Sonnet. DiagGuard: two-stage defense (Grounder surveys observations before localization; Verifier audits diagnosis).
- 评价指标: Acc@1, Node F1, Edge F1, causal-chain depth, reasoning budget (rounds, tokens, cost).
- 模型比较: Compared six frameworks under Qwen; isolated backbone effect by rerunning THINKDEPTH.AI on Claude Sonnet. DiagGuard validated on held-out setting (Seed 2.0 Pro, AIOps 2025).
- 我的理解: The authors treat RCA as an observable process, not just a label prediction. They manually annotate fault propagation paths (ground truth) and normalize agent trajectories to compare against these paths. This allows them to measure not just whether the root cause is found, but how the agent navigates the fault-impact surface and uses evidence.

### 6. 关键发现

- Disconnect between answer correctness and diagnostic quality: An agent may correctly localize the fault source but fail to reconstruct its propagation path. Recovering the path is harder and more discriminative than identifying affected services alone.
- Successful vs. failing diagnostic processes: Successful investigations stay on the fault-impact surface, act on retrieved evidence, and broaden query repertoire as search deepens. Failures arise from evidence omission, misinterpretation, or unsupported inference.
- DiagGuard improves RCA accuracy: In a held-out setting (different model, benchmark, topology), DiagGuard raises Acc@1 from 43.5% to 52.5% by grounding and verification stages.

### 7. 最重要的图

- 图来源: Figure 1 (in paper): Outcome-level vs. trajectory-level evaluation
- 为什么重要: Illustrates that a wrong diagnosis can still have correct final answer if the agent reaches the fault source but omits decisive evidence before reporting. This motivates the need for trajectory-level evaluation.

### 8. 如何读这张图

The figure shows two columns: left side shows outcome-level metrics (Acc@k, MRR, MAP) that only capture final answer; right side shows the agent's reasoning trajectory (steps 4-47) where it reaches the root cause service but leaves its metrics uninspected, leading to a wrong diagnosis. The trajectory reveals the evidence omission failure hidden by outcome metrics.

### 9. 次重要图

- 为什么也重要: Figure 2 (study overview) clarifies the two-phase methodology: Phase 1 collects 3,500 trajectories and annotates propagation paths; Phase 2 characterizes them at three levels (outcome, behavior, failure modes) and designs DiagGuard.

### 10. 对 Agent / Skill / Memory 的启发

- 对 Agent 系统: Agent systems for RCA should be evaluated not just on final answer but on the diagnostic process. Trajectory-level metrics (Node F1, Edge F1) reveal hidden failures.
- 对 Skill: Agents need skills to stay on the fault-impact surface, act on retrieved evidence, and broaden query repertoire as search deepens.
- 对 Memory: Memory of past queries and evidence is crucial to avoid shallow loops and evidence omission.
- 对评测: Evaluation should include process-level ground truth (fault propagation paths) and failure mode analysis to guide improvements.

### 11. 局限性

- Manual annotation of propagation paths is labor-intensive and may not scale to larger benchmarks.
- Only SQL-based telemetry interfaces are compared for trajectory analysis; other interfaces (e.g., API calls) may differ.
- DiagGuard validation is on a single held-out setting; generalizability to other models and topologies needs further study.

### 12. 我的看法 / 个人笔记

This paper makes a strong case for process-level evaluation in RCA. The trajectory-level framework is novel and the failure taxonomy is actionable. The DiagGuard defense shows practical improvement. However, the manual annotation effort limits scalability; future work could automate propagation path inference.

### 14. 总结

This paper introduces a trajectory-level evaluation framework for LLM-based microservice root cause analysis, using manually annotated fault propagation paths as ground truth. Analyzing 3,500 trajectories across six agent frameworks reveals that answer correctness often masks poor diagnostic quality. Successful agents stay on the fault-impact surface and act on evidence; failures stem from evidence omission, misinterpretation, or unsupported inference. The authors operationalize these failures into DiagGuard, a two-stage defense that improves Acc@1 from 43.5% to 52.5% on a held-out setting. The work highlights the need for process-level metrics and provides actionable failure patterns for improving automated RCA.

## 2. Benchmarking Patent Drafting from Inventor-Style Disclosures

**Topics:** Patent Drafting, Multi-Agent Systems, Large Language Models
**Authors:** Lekang Jiang, Wenjun Sun, Stephan Goetz
**Venue / Year:** arXiv 2026
**Links:** [Abstract](http://arxiv.org/abs/2608.21249v1) | [PDF](http://arxiv.org/pdf/2608.21249v1.pdf) | [Code](https://github.com/scylj1/Patent-MAF)

### 1. 一句话结论

本文提出Dis2Pat数据集和Patent-MAF多智能体框架，首次实现从发明人风格的非法律化披露直接生成完整专利，且Patent-MAF在本地开源模型上性能优于所有开源模型，与闭源模型竞争。

### 2. 为什么重要

专利起草是昂贵且关键的过程，现有基准多基于后期结构化输入，忽略实际工作流中从非正式发明披露开始的挑战。Dis2Pat填补了这一空白，而Patent-MAF通过多智能体协作和本地部署解决了隐私和长文本法律约束问题，为实际专利起草自动化提供了可行方案。

### 3. 研究问题

1. 如何从非法律化、发明人风格的披露直接生成完整且法律一致的专利申请书？
2. 多智能体框架能否在本地开源模型上实现与闭源模型竞争的专利起草性能？

### 4. 背景与问题设定

现有专利生成工作多假设输入为后期结构化或已法律化的文本（如完整说明书或权利要求），但实际中发明人提交的是非正式、去法律化的披露。此外，专利起草涉及长文本和法律约束，且发明披露通常包含敏感信息，需本地部署。Dis2Pat数据集通过LLM从授权专利构造伪披露，模拟真实场景；Patent-MAF则设计多智能体框架以应对这些挑战。

### 5. 方法概览

- 任务 / 环境: 从发明人风格的文本和附图生成完整专利申请书（权利要求和说明书）。
- 变量 / 干预设计: Patent-MAF包含三个角色：管理智能体（结构化披露并路由子任务）、起草智能体（专门生成权利要求和说明书）、润色智能体（统一术语、检查一致性）。所有智能体基于本地开源模型（Qwen3-32B和Qwen3-VL-32B），权利要求起草器经LoRA微调。
- 评价指标: 自动指标（BLEU、ROUGE-1、ROUGE-L）、LLM-as-a-judge质量评估、专家人工评估。
- 模型比较: 对比开源模型（Qwen3-32B、LLaMA-3.3-70B等）和闭源模型（GPT-4o、GPT-5），以及多模态变体。Patent-MAF在所有开源模型中表现最佳，与GPT-5竞争。
- 我的理解: 该方法通过分解任务（管理、起草、润色）并利用微调后的专用模型，有效处理了从非结构化披露到法律结构化文档的转换，同时通过本地部署满足隐私需求。

### 6. 关键发现

- Dis2Pat数据集质量高且忠实于原始专利: 通过人工评估，伪披露在幻觉、细节缺失、矛盾、去法律化四个维度均获得9.7分以上（10分制），且ROUGE-L仅0.08，表明内容忠实但非词汇复制。
- Patent-MAF在开源模型中表现最优: 在自动指标和LLM评估中，Patent-MAF一致优于所有开源基线（如Qwen3-32B、LLaMA-3.3-70B），并与GPT-4o和GPT-5竞争，尤其在权利要求生成上通过微调显著提升。
- 多智能体协作和微调是关键组件: 消融实验显示，移除管理智能体、视觉输入或润色智能体均导致性能下降，表明每个组件对最终质量均有贡献。

### 7. 最重要的图

- 图来源: 图1：Patent-MAF方法概览
- 为什么重要: 该图清晰展示了多智能体框架的工作流：管理智能体结构化披露，起草智能体分别生成权利要求和说明书，润色智能体最终优化，直观体现了任务分解和协作机制。

从左侧输入（专利披露文本和附图）开始，管理智能体将其分为两份起草材料（分别用于权利要求和说明书），然后两个起草智能体独立生成对应部分，最后润色智能体合并并优化输出完整专利。

### 10. 对 Agent / Skill / Memory 的启发

- 对 Agent 系统: 多智能体框架通过角色分解（管理、起草、润色）有效处理复杂长文本生成任务，可推广至其他法律文档生成场景。

- 对 Memory: 管理智能体通过结构化披露为后续生成提供上下文，减少了长文本中的信息丢失。
- 对评测: 结合自动指标、LLM评估和人工评估的多维度评价体系，为法律文档生成提供了更全面的评估范式。

### 11. 局限性

- 伪披露由LLM生成，可能无法完全模拟真实发明披露的多样性和噪声。
- 数据集仅包含授权专利，未覆盖驳回或未授权案例，可能引入偏见。
- Patent-MAF依赖多个模型，计算成本较高，且未探索更高效的模型压缩或蒸馏方法。

### 12. 我的看法 / 个人笔记

该工作通过构建更真实的基准和提出实用的多智能体框架，推动了专利起草自动化领域的发展。其本地部署设计符合实际隐私需求，但伪披露的构造方法需进一步验证其泛化性。未来可探索从真实发明披露（如企业内数据）构建数据集，或引入交互式反馈机制。

### 14. 总结

## 3. OmniAssistBench: Assistant-style Interaction Benchmark for Omni-LLMs

**Topics:** GUI Agent, Omni-LLM, Benchmark, Interactive Video Understanding
**Authors:** Xianyun Sun, Chaoyou Fu, Zhengye Zhang, Feiyang Duan, Qingyuan Cao, Yonghui Niu, Sihang Yuan, Ge Zhang, Caifeng Shan
**Venue / Year:** arXiv 2026
**Links:** [Abstract](http://arxiv.org/abs/2608.21360v1) | [PDF](http://arxiv.org/pdf/2608.21360v1.pdf) | [Code](https://xianyunsun.github.io/OmniAssistBench/)

### 1. 一句话结论

OmniAssistBench 通过逆向工程互联网视频构建多轮交互基准，揭示当前 Omni-LLM 在视觉提示跟随、长期记忆和延迟响应方面的严重不足。

### 2. 为什么重要

该工作首次系统性地解决了交互式视频助手评估中路径发散和动态反馈的难题，为 Omni-LLM 从被动理解向主动助手演进提供了关键测试平台。

### 3. 研究问题

1. 如何构建一个能反映真实交互动态的离线评估基准？
2. 当前 Omni-LLM 在哪些核心能力上仍不足以成为可靠的实时视频助手？

### 4. 背景与问题设定

传统视频理解基准使用静态问答对，无法模拟助手响应改变用户后续行为导致的路径发散。OmniAssistBench 通过从源视频提取先验知识强制固定交互路径，并逆向工程互联网视频来模拟多轮交互。

### 5. 方法概览

- 任务 / 环境: 300 个视频，685 个 QA 对，涵盖基本感知和高级目标导向任务，包括 3 个自拍真实案例（平均 15 轮交互）。
- 变量 / 干预设计: 将用户提示嵌入视频末尾（音频或画中画），确保时间因果连续性；通过先验知识固定交互路径，避免路径发散。
- 评价指标: 开放问答，结合语义相似度和关键点包含率，惩罚冗余和幻觉信息。
- 模型比较: Gemini-3-Pro (66.4/100) > Qwen3-Omni-Instruct (51.2/100)，开源模型显著落后。
- 我的理解: 该基准通过精心设计的先验知识和视频编辑，将动态交互问题转化为可控的离线评估，但人工标注成本极高（>1000 专家小时）。

### 6. 关键发现

- 视觉提示跟随缺陷: 模型难以理解手势等视觉提示，例如在 Gesture-based Prompt Following 任务中表现不佳。
- 长期记忆与上下文保持不足: 多轮交互中模型容易忘记初始用户目标，且上下文窗口在几分钟内耗尽。
- 延迟响应失败: 模型常立即回复无关描述，而非等待目标事件发生后再响应。

- 图来源: Figure 1 (c) - 数据标注方法示意图
- 为什么重要: 直观展示了如何通过先验知识固定交互路径，解决路径发散问题，是基准构建的核心创新。

左侧展示传统视频理解中模型响应不影响视频内容；中间展示助手模型可能引导用户走不同路径导致数据不匹配；右侧展示 OmniAssistBench 通过从视频中提取先验知识（如制作拿铁的步骤顺序）强制模型沿固定路径引导用户。

### 10. 对 Agent / Skill / Memory 的启发

- 对 Agent 系统: 需要设计更鲁棒的视觉提示理解和长期记忆机制，以支持多轮交互。
- 对 Skill: 模型应具备延迟响应能力，即等待特定事件发生后再生成回答。
- 对 Memory: 需要更高效的长上下文管理策略，避免跨轮遗忘。
- 对评测: 开放问答和关键点匹配的评估方法可推广到其他交互式基准。

### 11. 局限性

- 人工标注成本极高，难以大规模扩展。
- 固定交互路径可能无法覆盖真实世界中所有可能的用户行为。
- 仅评估了英文场景，未涉及多语言或跨文化交互。

### 12. 我的看法 / 个人笔记

OmniAssistBench 是交互式视频助手评估的重要进步，但其人工密集型构建方式限制了可扩展性。未来可探索半自动或基于模拟的数据生成方法。

### 14. 总结

OmniAssistBench 通过逆向工程互联网视频和先验知识固定交互路径，构建了首个面向 Omni-LLM 的交互式助手基准。评估显示当前模型在视觉提示跟随、长期记忆和延迟响应方面存在显著不足，为未来研究指明了方向。

## 4. Natural-Language Workflows Are Not Software Yet: Artifact-Driven Compilation for Reliable Agent Execution

**Topics:** AI Agent, Workflow Compilation, Software Engineering
**Authors:** Xiangzhe Xu, Hanxi Guo, Guangyu Shen, Siyuan Cheng, Xiangyu Zhang
**Venue / Year:** arXiv 2026
**Links:** [Abstract](http://arxiv.org/abs/2608.21341v1) | [PDF](http://arxiv.org/pdf/2608.21341v1.pdf)

### 1. 一句话结论

ARTIC通过工件驱动编译将自然语言工作流转化为显式数据依赖和控制流表示，任务解决率提升28个百分点，跨模型和重复执行一致性分别提升32和56个百分点。

### 2. 为什么重要

自然语言工作流作为智能体可执行指令的可靠性不足，ARTIC通过编译优化和忠实性验证，显著提升了智能体执行复杂工作流的准确性和一致性，为构建可靠智能体系统提供了新范式。

### 3. 研究问题

1. 如何将自然语言工作流转化为可分析、可优化的显式表示以提升智能体执行可靠性？
2. 如何验证LLM辅助编译后的工作流是否忠实于原始自然语言工作流？

### 4. 背景与问题设定

自然语言工作流允许领域专家编写可复用流程并由智能体执行，但存在两大问题：数据依赖隐式化导致智能体需自行推断相关结果，以及长指令或分支指令在上下文压力下易被错误执行。现有方法依赖无约束LLM决策或人工审查，缺乏可靠性保障。

### 5. 方法概览

- 任务 / 环境: 11个真实领域工作流，共488个问题实例，涵盖医疗转诊等场景。
- 变量 / 干预设计: ARTIC编译器将自然语言工作流转化为工件驱动工作流：每个步骤声明读写工件，约束门控产出工件，显式控制转移路由执行。通过约束优化识别依赖过多状态或复杂控制逻辑的步骤并分解。优化目标包括：控制流复杂度（基于圈复杂度估计）、上下文压力（基于上下文长度估计）、工件数量（每个步骤的工件数）、以及工件可压缩性（基于活工件数）。
- 评价指标: 任务解决率（task resolve rate）、跨模型一致性（cross-model consistency）、重复执行一致性（repeated-execution consistency）。
- 模型比较: 与原始文本工作流对比，ARTIC编译后工作流任务解决率提升28个百分点；跨模型和重复执行一致性分别提升32和56个百分点。消融实验表明，缺少忠实性验证的编译器变体性能下降16个百分点。
- 我的理解: ARTIC的核心创新在于将自然语言工作流转化为半结构化表示，使数据依赖和控制流显式化，从而可分析执行负担并优化。同时，通过局部义务分解和场景化模拟验证忠实性，解决了LLM编译结果不可信的问题。例如，在患者转诊工作流中，编译器将原始决策步骤分解为风险评分计算、复杂护理资格检查和慢性护理资格检查三个子步骤，每个子步骤只接收必要的工件（如风险评分步骤只接收利用数据），从而降低上下文压力。

### 6. 关键发现

- 工件驱动编译显著提升任务解决率: 在488个问题实例上，ARTIC编译后的工作流任务解决率比原始文本工作流高28个百分点。
- 编译后工作流跨模型和重复执行一致性更高: ARTIC编译的工作流在跨模型设置中一致性提升32个百分点，在重复执行设置中提升56个百分点。
- 忠实性验证对性能至关重要: 消融实验表明，缺少忠实性验证的编译器变体性能下降16个百分点，说明验证环节不可或缺。

### 10. 对 Agent / Skill / Memory 的启发

- 对 Agent 系统: ARTIC提供了一种将自然语言工作流编译为可执行、可验证形式的方法，使智能体系统能更可靠地执行复杂领域流程，减少因上下文混乱或控制流误解导致的错误。
- 对 Skill: 工件驱动表示将技能分解为原子步骤，每个步骤有明确输入输出，便于技能复用和组合，同时降低了对智能体推理能力的要求。
- 对 Memory: 显式工件声明减少了智能体需要维护的隐式上下文，通过限制每个步骤的工件数量，降低了上下文压缩压力，提升了记忆可靠性。
- 对评测: ARTIC的忠实性验证方法（局部义务分解+场景化模拟）为评估自然语言到结构化工作流转换提供了新范式，可推广到其他LLM辅助编译场景。

### 11. 局限性

- ARTIC依赖LLM进行编译和验证，LLM的推理能力可能成为瓶颈，尤其在复杂领域。
- 当前评估限于11个领域工作流，泛化性需更多验证。
- 工件驱动语言表达能力有限，可能无法覆盖所有自然语言工作流中的细微语义。

### 12. 我的看法 / 个人笔记

ARTIC巧妙地将软件工程中的编译思想引入智能体工作流领域，通过显式化数据依赖和控制流解决了自然语言指令执行不可靠的核心问题。其忠实性验证方法尤其值得关注，为LLM辅助代码生成或转换提供了可借鉴的验证范式。未来工作可探索更丰富的工件类型和更复杂的控制结构，以及将编译优化与在线学习结合。

### 14. 总结

ARTIC提出工件驱动工作流编译器，将自然语言工作流转化为显式声明数据依赖和控制流的半结构化表示，通过约束优化（包括控制流复杂度、上下文压力、工件数量和可压缩性等目标）分解复杂步骤，并通过局部义务验证和场景化模拟确保忠实性。在11个真实领域工作流上，任务解决率提升28个百分点，跨模型和重复执行一致性分别提升32和56个百分点，显著提升了智能体执行自然语言工作流的可靠性。

## 5. From Regulation to Implementation: A Critical Evaluation of LLM-Assisted Regulatory Compliance in Industry

**Topics:** LLM应用, 法规合规, 数字产品护照, 数据保护影响评估, 提示工程
**Authors:** Adriana Watson, Marco Bücheler, Grant Richards
**Venue / Year:** arXiv:2608.21317v1
**Links:** [Abstract](http://arxiv.org/abs/2608.21317v1) | [PDF](http://arxiv.org/pdf/2608.21317v1.pdf)

### 1. 一句话结论

LLM生成的合规文档质量受提示上下文影响：结构严格的数字电池护照（DBP）输出一致但易产生幻觉，而结构模糊的数据保护影响评估（DPIA）需要更丰富的上下文提示以保持完整性和一致性。

### 2. 为什么重要

该研究首次系统评估了提示策略对LLM生成法规合规文档的影响，揭示了不同法规严格程度下LLM输出的差异，为工业自动化合规提供了关键指导。

### 3. 研究问题

1. 数据提取指令和法规模糊性如何影响LLM生成的合规文档质量和一致性？
2. 不同严格程度的法规（如DBP和DPIA）对LLM输出有何不同影响？

### 4. 背景与问题设定

欧盟的ESPR和GDPR法规要求企业生成合规文档（如DPP和DPIA），但工业数据分散、格式异构，且DPIA缺乏标准化格式，使得手动创建困难。研究者提出使用LLM辅助生成，但现有研究未充分探讨数据提取指令和法规模糊性对LLM输出的影响。

### 5. 方法概览

- 任务 / 环境: 使用5种LLM（GPT-4o、Claude 4.6 Sonnet、Meta-Llama-3.1-8B-Instruct、Mistral-7B、Qwen2.5-7B-Instruct）生成DBP和DPIA文档。
- 变量 / 干预设计: 对每个任务设置4种提示模糊度水平（基线、高、中、低），每种模型运行3次，共120次实验。DBP提示基于AAS模板，DPIA提示基于GDPR Article 35(7)。
- 评价指标: 将LLM输出与手动创建的金标准模式进行对比，评估完整性和一致性。
- 模型比较: 比较5种模型在不同提示水平下的输出质量，但未详细报告各模型具体性能差异。
- 我的理解: 实验设计通过控制提示上下文丰富度，模拟了法规明确性（DBP）和模糊性（DPIA）两种极端情况，从而揭示LLM在不同法规环境下的表现差异。

### 6. 关键发现

- 严格法规下LLM输出一致但易幻觉: 对于结构严格的DBP，无论提示上下文如何，LLM输出结果一致，但可能产生更多幻觉（如虚构数据）。
- 模糊法规需要更高上下文提示: 对于结构模糊的DPIA，需要更高上下文的提示才能保持输出的完整性和一致性。

### 10. 对 Agent / Skill / Memory 的启发

- 对 Agent 系统: LLM代理在生成合规文档时需根据法规严格程度调整提示策略，严格法规下需防幻觉，模糊法规下需丰富上下文。
- 对 Skill: 提示工程技能需针对不同法规定制，包括如何提供结构化模板和领域知识。
- 对 Memory: LLM记忆中的训练数据可能导致幻觉，需结合RAG或外部知识库提高准确性。
- 对评测: 评估LLM生成合规文档时，需同时考虑完整性和一致性，并针对不同法规制定不同标准。

### 11. 局限性

- 仅使用单一产品（BoilerCell电池）和单一场景（物流运营商），结果泛化性有限。
- 未评估LLM输出的隐私风险和数据泄露问题。
- 金标准模式由研究者手动创建，可能引入主观偏差。

### 12. 我的看法 / 个人笔记

该研究为LLM在法规合规中的应用提供了重要实证，但需进一步探索如何平衡严格法规下的幻觉问题与模糊法规下的上下文需求。未来可结合RAG和领域微调来提升可靠性。
