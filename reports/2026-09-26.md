## 1. Screen Before You Serve: Simulation for Production Customer Experience AI Agents at 140M Scale

**Topics:** GUI Agent, Customer Experience AI, Simulation-based Evaluation, LLM Agents
**Authors:** Edesio Alcoba, Kevin Rossell, Aman Gupta, Shao Tang, Jiwoo Hong, Pabel Carrillo-Mendoza, Wanderson Conceição Ferreira, Alvaro Tedeschi, Zayd Simjee, Shreya Rajpal, Bruno Finardi Hime, Christian Sousa, Luis Moneda, Herbert Fei, Daniel Silva, Rohan Ramanath
**Venue / Year:** arXiv preprint, September 2026
**Links:** [Abstract](http://arxiv.org/abs/2609.30137v1) | [PDF](http://arxiv.org/pdf/2609.30137v1.pdf)

### 1. 一句话结论

提出一种基于假设驱动的工具边界仿真工作流，在部署前筛选客户体验AI代理，显著提升生产指标（tNPS +36.69，SSR +8.82个百分点）。

### 2. 为什么重要

在受监管行业中，直接对客户进行实验风险高且成本大。该工作提供了一种安全、可扩展的离线评估方法，使代理迭代速度提升4.8倍，并能在不暴露真实客户的情况下探索大量模型和配置，为生产级AI代理的可靠部署提供了实用范式。

### 3. 研究问题

1. 如何在不影响真实客户体验的前提下，安全地评估和筛选生产级客户体验AI代理？
2. 仿真生成的对话与真实对话在多大程度上相似，且仿真评估结果能否预测线上表现？

### 4. 背景与问题设定

客户体验（CX）代理需处理意图识别、策略遵循和工具调用等复杂任务，尤其在金融等受监管行业，安全性和可靠性要求极高。传统手工测试覆盖有限，而线上A/B测试会让客户暴露于失败风险中。因此，需要一种中间评估层，在部署前对候选代理进行筛选。

### 5. 方法概览

- 任务 / 环境: Nubank的Card Delivery（CD）代理及其扩展版Card Management（CM）代理，后者是巴西最高流量的聊天支持代理。
- 变量 / 干预设计: 使用Snowglobe模拟器生成合成客户与代理的多轮对话，工具调用由模拟层响应，不调用生产后端。通过假设驱动的筛选流程，比较候选代理与当前代理的模拟轨迹。
- 评价指标: 离线评估使用LLM-as-a-Judge（GPT-4.1-Mini）对五个语义类别进行二元评分；线上评估使用tNPS（交易净推荐值）和SSR（自助服务率）。
- 模型比较: 比较了Snowglobe模拟器与朴素LLM基线（gpt-5.6-sol）的仿真质量，并通过余弦距离、评估分数相关性等指标验证仿真与真实对话的相似性。
- 我的理解: 该方法的核心在于“工具边界”仿真：模拟用户与代理交互，但工具调用由模拟器响应，从而在不影响生产环境的情况下测试代理的决策和对话能力。通过假设驱动的筛选，即使仿真不完全精确，也能捕捉到影响部署决策的关键差异。

### 6. 关键发现

- 仿真与生产高度相关: 在四个部署版本中，模拟与生产的版本级二元评估分数高度相关，且模拟对话与真实对话的余弦距离最低达0.035，表明仿真能有效反映真实表现。
- 仿真指导的迭代带来显著线上提升: 通过仿真筛选的CM代理在线上A/B测试中，tNPS提升36.69点，SSR提升8.82个百分点，达到Nubank历史最高水平，且无统计显著的tNPS下降。
- 开发周期加速4.8倍: 引入仿真层后，从开发到部署的周期从数月缩短至数天，效率提升4.8倍，使团队能探索更多模型和配置。

## 2. Multimodal Thinking with Renderable Programs

**Topics:** GUI Agent, 视觉语言模型, 可渲染程序, SVG, 多模态推理
**Authors:** Sunli Chen, Ding Zhong, Ziqiao Ma, Jiaxin Liu, Zeyuan Yang, Hao Zhang, Lie Lu, Joyce Chai, Chuang Gan
**Venue / Year:** arXiv 2026
**Links:** [Abstract](http://arxiv.org/abs/2609.30130v1) | [PDF](http://arxiv.org/pdf/2609.30130v1.pdf)

### 1. 一句话结论

SVGLM 通过将 SVG 作为可渲染程序融入推理链，使视觉语言模型能够在推理过程中生成和操作图像，从而在数学推理任务上显著超越现有方法。

### 2. 为什么重要

当前视觉语言模型在视觉理解和文本推理上表现出色，但难以在推理过程中主动生成和操作图像。SVGLM 利用 SVG 的声明性、可编辑性和语义明确性，为多模态推理提供了一种紧凑、可解释且可验证的中间表示，有望推动数字智能体在需要视觉操作的复杂任务中的发展。

### 3. 研究问题

1. 如何让视觉语言模型在推理过程中生成和操作图像，以增强其多模态推理能力？
2. SVG 作为可渲染程序，能否有效桥接文本推理与像素图像之间的鸿沟？

### 4. 背景与问题设定

视觉语言模型（VLMs）在视觉内容理解和文本推理方面表现出色，但其结构限制了将图像融入推理链的能力。尽管全模态模型尝试统一文本和图像生成，但它们在开放域视觉任务中缺乏可追踪性，因为图像通常以栅格或潜在表示形式存在。此外，现有 VLMs 在处理数学图表等结构化视觉信息时表现不佳，且其推理步骤往往缺乏视觉证据的支撑。

### 5. 方法概览

- 任务 / 环境: 数学推理任务，特别是平面几何和立体几何问题，需要绘制辅助线或进行视觉操作。
- 变量 / 干预设计: SVGLM 采用标准的多轮工具调用范式，允许模型在生成文本的过程中随时调用 SVG 渲染工具，将生成的 SVG 代码渲染为图像并作为后续推理的视觉上下文。
- 评价指标: 在 MathCanvas-Bench 基准上，使用加权准确率（weighted accuracy）评估，其中后续子问题的权重更高。
- 模型比较: 比较了三种开源模型（LLaVa-Next-Mistral-7B、Qwen2.5-VL-7B、InternVL-3-8B）在零样本、标准 SFT 和 SVGLM 三种设置下的性能，并与商业模型 GPT-4o 及现有方法 V-Thinker、Qwen-Image-Edit 等对比。
- 我的理解: SVGLM 的核心创新在于将 SVG 作为推理的“可执行”中间表示，模型不仅生成文本推理，还能生成 SVG 代码来绘制辅助线或标记，从而将视觉操作显式地融入推理链。这种方法利用了 SVG 的声明性和可编辑性，使得每一步视觉修改都是可验证和可纠正的，避免了栅格图像或隐式表示的不可追踪性。

### 6. 关键发现

- SVGLM 显著提升数学推理性能: 在 MathCanvas-Bench 上，SVGLM 在所有三个开源模型上都取得了最佳成绩，例如 Qwen2.5-VL-7B 的加权准确率从 21.8 提升到 30.9，超过了 GPT-4o 的 19.2。
- SVG 生成质量高: 人工评估显示，79.5% 的生成 SVG 能完美重构目标图像，仅 1% 存在结构性错误，验证了数据质量和模型生成能力。
- 图像编辑模型难以胜任视觉推理: 对比实验显示，Qwen-Image-Edit 和 Nano-Banana 等图像编辑模型在遵循指令生成辅助线时存在严重幻觉和领域错位，而 SVGLM 生成的 SVG 则准确且可编辑。

### 10. 对 Agent / Skill / Memory 的启发

- 对 Agent 系统: SVGLM 展示了将可渲染程序作为工具调用集成到智能体系统中的可行性，为数字智能体提供了更可靠的视觉操作能力，可应用于需要动态视觉反馈的复杂任务。
- 对 Skill: SVG 生成可视为一种新的技能，模型通过微调即可掌握，无需额外工具或环境，降低了技能获取成本。
- 对 Memory: SVG 作为紧凑的文本表示，可高效存储和复用，有助于智能体在长期任务中维护视觉状态。
- 对评测: SVGLM 的评估方法（加权准确率）强调了后续推理步骤的重要性，为多模态推理评估提供了参考。

### 11. 局限性

- SVGLM 目前仅在数学推理任务上验证，其泛化性到其他领域（如自然图像编辑）尚待探索。
- 数据构建依赖商业模型（如 Gemini-3.0-Thinking）生成 SVG，可能引入偏差或错误。
- SVG 生成能力受限于模型规模，更大模型可能进一步提升性能，但计算成本增加。

### 12. 我的看法 / 个人笔记

SVGLM 提出了一种优雅且实用的方法，将 SVG 作为多模态推理的中间表示，有效解决了 VLMs 在推理中缺乏视觉操作能力的问题。其数据构建流程和质量控制值得借鉴。未来工作可探索将 SVG 与其他可编程表示（如 LaTeX 或 TikZ）结合，或扩展到更广泛的视觉推理任务。

## 3. KernelOPT: Dispatch-Aware Agentic Search for GPU Kernel Optimization

**Topics:** GPU内核优化, LLM智能体, 编译器感知优化, Triton内核, 多智能体系统
**Authors:** Aheli Poddar, Sanskar Prasad, Arindam Samanta, Subha Chakraborty, Vishal Goyal, Rohit Singh Rathaur
**Venue / Year:** arXiv 2026
**Links:** [Abstract](http://arxiv.org/abs/2609.30059v1) | [PDF](http://arxiv.org/pdf/2609.30059v1.pdf) | [Code](https://github.com/TorchedHat/KernelOPT)

### 1. 一句话结论

KernelOPT通过尊重编译器调度决策、聚焦优化Triton子内核，并采用四门验证级联，在250个KernelBench问题上实现了相对torch.compile的几何平均加速1.40倍（L1）、1.15倍（L2）和1.07倍（L3）。

### 2. 为什么重要

该工作首次将编译后的模型视为结构化产物，而非黑盒，通过保留cuBLAS/cuDNN等库调用，仅优化生成的Triton内核，并引入模型级端到端验证，解决了现有LLM内核优化工具缺乏整体验证和编译器感知的问题，显著提升了实际模型性能。

### 3. 研究问题

1. 如何利用编译器调度结构（如保留库调用）来指导LLM优化编译后的模型？
2. 如何设计一个多智能体系统，在优化GPU内核时同时保证正确性和性能？
3. 如何通过模型级验证和性能门控确保优化后的内核在端到端场景中有效？

### 4. 背景与问题设定

深度学习推理和训练性能高度依赖GPU内核效率。PyTorch Inductor等编译器自动生成的内核往往远逊于专家手写实现。现有LLM辅助优化工具通常将编译后的模型视为黑盒，仅优化独立内核，缺乏对编译器结构决策的尊重和端到端验证。KernelOPT旨在解决这一问题，通过感知编译器调度，优化生成的Triton子内核，并在模型级别验证正确性和性能。

### 5. 方法概览

- 任务 / 环境: NVIDIA H200 GPU，PyTorch Inductor编译的模型，KernelBench基准（250个问题）及20个教程内核。
- 变量 / 干预设计: 多智能体系统（5个智能体：规划器、执行器、分析器、总结器、配置文件解析器）在LangGraph状态机中协作，使用NCU硬件性能分析指导优化，并采用四门验证级联（静态验证、多种子正确性、模型级浮点64位回退验证、性能门控）。
- 评价指标: 几何平均加速比（相对torch.compile）、正确性（allclose容差）、端到端模型级性能。
- 模型比较: 与torch.compile基线比较，并提及与KernelAgent、AccelOpt、K-Search等现有LLM优化工具的差异（但未直接数值对比）。
- 我的理解: 该方法的核心创新在于将编译器调度视为先验知识，通过保留库调用和聚焦Triton内核，结合多智能体协作和严格的验证流程，实现了安全且高效的自动优化。

### 6. 关键发现

- 显著加速效果: 在250个KernelBench问题上，KernelOPT实现了几何平均加速1.40倍（L1）、1.15倍（L2）和1.07倍（L3），其中94个内核被优化，58个匹配，85个回退到基线。
- 算法优化和算子融合是主要加速来源: 最大加速来自结构性重写（如对角矩阵乘法从O(N^3)降至O(N^2)，加速88.63倍）和算子融合（如L2 018融合5个操作，加速33.11倍）。
- 库调用主导导致回退: 85个回退案例中，61个因cuBLAS/cuDNN主导（占72%），15个因性能门控拒绝，7个因无Triton内核，2个因端到端正确性失败。
