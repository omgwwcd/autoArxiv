## 1. RL-Guided Temporal Localization for Dual-Channel Retrieval in Long-Horizon Agent Memory

**Topics:** Long-Horizon Agent Memory, Time-Aware Retrieval, Reinforcement Learning, Retrieval-Augmented Generation
**Authors:** Dabin Sheng, Zhe Wu, Jinming Zhao, Junliang Xing, Yuanchun Shi
**Venue / Year:** NeurIPS 2026
**Links:** [Abstract](http://arxiv.org/abs/2610.23598v1) | [PDF](http://arxiv.org/pdf/2610.23598v1.pdf)

### 1. 一句话结论

TIDER通过强化学习训练的轻量级时序区间定位器，在检索阶段显式预测证据所在时间窗口，并与语义通道并行检索、按时间距离重排，显著提升了长时记忆智能体在时间敏感查询上的准确率。

### 2. 为什么重要

长时记忆智能体面临大量语义相似但时间不同的事件，现有方法在检索阶段忽略时间约束，导致目标记忆被错误候选淹没。TIDER首次将时间约束显式引入检索阶段，通过强化学习优化离散的窗口定位决策，为长时记忆检索提供了新范式，显著提升时间敏感查询的准确性。

### 3. 研究问题

1. 如何在检索阶段显式利用时间约束，避免目标记忆被语义相似但时间不匹配的候选淹没？
2. 如何通过强化学习训练一个轻量级时序区间定位器，使其能准确预测证据所在的时间窗口？

### 4. 背景与问题设定

长时记忆智能体需要从持续增长的历史事件中检索相关证据，但日常事件在语义上高度同质（如“和家人吃晚餐”一年内可能重复数百次），区分不同事件的关键往往在于时间。现有方法在记忆组织或答案生成阶段注入时间信息，但忽略了检索阶段——候选集一旦被污染，后续推理无法弥补。TIDER受人类情景记忆中时间邻近效应的启发，提出在检索阶段显式预测时间窗口，并构建双通道检索框架。

### 5. 方法概览

- 任务 / 环境: 长时记忆问答任务，输入为多轮对话历史C和查询q，输出为证据集E_hat供下游LLM生成答案。
- 变量 / 干预设计: TIDER包含一个强化学习训练的时序区间定位器πθ，输入为查询q和查询相关的时间线摘要S_q（由top-30相关时间线条目构成），输出结构化定位z=(detect, W_pred)，其中detect指示是否时间敏感，W_pred为预测的时间窗口。预测窗口定义时间通道，与语义通道并行检索，合并后按时间距离衰减重排。
- 评价指标: 在LifeBench和LoCoMo上评估准确率（Accuracy）和F1分数。
- 模型比较: 与三类基线比较：智能体记忆框架（MemOS、TiMem、Zep、Mem0）、时间感知检索（TsContriever）、时间推理（NeSTR），所有方法共享相同的下游答案模型和top-k检索预算，并报告Oracle上界。
- 我的理解: TIDER的核心创新在于将时间约束从向量空间解耦，用显式时间窗口表达，并通过强化学习优化窗口定位。双通道设计平衡了语义和时间信号，重排机制抑制了时间不匹配的干扰项。

### 6. 关键发现

- SOTA性能: 在LifeBench上总体准确率61.52%，比最强基线（NeSTR）高8.82个百分点；在LoCoMo上78.96%，比最强基线高3.66个百分点。
- 时间通道和重排机制的必要性: 消融实验表明，移除时间通道或重排机制会显著降低性能，尤其在需要区分语义相似但时间不同事件的困难查询上。
- 轻量级定位器的有效性: 仅用1.7B参数的定位器即可实现显著提升，表明强化学习训练的有效性。

### 11. 局限性

- 定位器依赖查询相关的时间线摘要，摘要质量可能影响性能。

- 实验仅在合成数据（LifeBench）和对话数据（LoCoMo）上验证，真实场景的泛化性有待测试。

## 2. On the possibilities and limitations of LLM-based multi-agent systems for multi-criteria decision-making in healthcare operations management

**Topics:** 多智能体系统, 大语言模型, 多准则决策, 医疗运营管理, 鲁棒优化
**Authors:** Marco Boresta, Tommaso Giovannelli, Sepehr Namirad, Giulia Riccardi
**Venue / Year:** 2026
**Links:** [Abstract](http://arxiv.org/abs/2610.23673v1) | [PDF](http://arxiv.org/pdf/2610.23673v1.pdf)

### 1. 一句话结论

LLM代理生成的偏好权重在医疗多准则决策中不可靠，需通过鲁棒优化来应对其不确定性。

### 2. 为什么重要

该研究首次系统评估了LLM多智能体系统在医疗运营管理中生成偏好权重的可靠性，并提出了一个通用框架（LLM-PADA）来审计这些偏好，确保其在优化决策中的安全使用。

### 3. 研究问题

1. LLM代理生成的显式偏好（评分）和隐式偏好（成对选择）是否可靠？
2. LLM代理的偏好不确定性如何影响最终决策？

### 4. 背景与问题设定

医疗运营决策（如门诊预约排程、急诊科配置）涉及多个相互冲突的目标（如患者等待时间、医生工作量、运营成本），需要权重来权衡。传统方法难以量化这些权重，而LLM代理可代表不同利益相关者提供权重，但其可靠性未知。

### 5. 方法概览

- 任务 / 环境: 两个医疗场景：门诊预约排程（显式偏好）和急诊科低危患者分流配置（隐式偏好）。
- 变量 / 干预设计: 显式偏好：让代理（分诊、医生、调度员）对三个准则的重要性评分（1-9），然后通过三种协议修订：数值交换、论证交换、机械平均。隐式偏好：让代理在成对配置中选择，配置由两个结果描述（平均等待时间、每周MIU开放时间）。
- 评价指标: 显式偏好：评分对情境的敏感性、角色差异、协议间一致性。隐式偏好：选择模型的预测准确性（考虑呈现顺序）。
- 模型比较: 比较了LLM代理的偏好与机械平均的差异，以及不同协议（数值、论证、机械）对偏好一致性和角色差异的影响。
- 我的理解: 该框架通过内部一致性检查（如情境敏感性、角色分化）来评估LLM偏好的可靠性，而非与人类偏好对比，因为人类偏好难以获取。

### 6. 关键发现

- 显式偏好受协议影响: LLM代理的评分对情境有响应，但论证协议会削弱情境敏感性，且机械平均保留角色差异，而LLM协商可能消除或逆转角色差异。
- 隐式偏好存在顺序偏差: 代理的成对选择受选项呈现顺序影响，且结果差异对预测的贡献有限，仅少数模型和角色组合能超越仅用顺序的基准。
- 鲁棒优化改变决策: 在大多数比较中，使用鲁棒加权和模型（考虑权重不确定性）选择的方案与使用平均权重选择的方案不同，表明忽略不确定性可能导致次优决策。

## 3. CocoRNA: Collective RNA Design with Cooperative Multi-agent Reinforcement Learning

**Topics:** RNA inverse design, multi-agent reinforcement learning, cooperative MARL, biological sequence design
**Authors:** Tianmeng Hu, Biao Luo, Ke Li
**Venue / Year:** ICML 2026
**Links:** [Abstract](http://arxiv.org/abs/2610.23820v1) | [PDF](http://arxiv.org/pdf/2610.23820v1.pdf)

### 1. 一句话结论

CocoRNA 通过合作式多智能体强化学习框架，将 RNA 逆向设计分解为多个子问题，显著提升了设计成功率与速度。

### 2. 为什么重要

RNA 二级结构对功能至关重要，但逆向设计面临组合爆炸、稀疏奖励等挑战。CocoRNA 首次将 MARL 应用于该问题，不仅大幅超越现有方法，还为其他复杂生物序列设计提供了新范式。

### 3. 研究问题

1. 如何利用多智能体协作解决 RNA 逆向设计中的组合爆炸与稀疏奖励问题？
2. CocoRNA 在成功率与设计速度上能否超越现有最先进方法？

### 4. 背景与问题设定

RNA 序列设计是逆向问题：给定目标二级结构（点括号表示），需找到能折叠成该结构的序列。序列空间随长度指数增长（4^ℓ），且存在多个序列对应同一结构。现有方法如 LEARNA 等基于单智能体 RL，面临样本效率低、易陷入局部最优等问题。

### 5. 方法概览

- 任务 / 环境: RNA 逆向设计环境：输入目标二级结构，输出 RNA 序列，通过 ViennaRNA 预测折叠结构并与目标比较。
- 变量 / 干预设计: 采用 Dec-POMDP 建模，多个智能体协作生成序列。提出两种分解方案：基于位置（将序列分段）和基于结构类型（如茎、环）。每个智能体观察局部窗口，动作空间为四种核苷酸。
- 评价指标: 成功率（精确结构匹配）和多样性（生成序列间的平均归一化汉明距离）。
- 模型比较: 与 antaRNA、LEARNA、Meta-LEARNA-Adapt、SAMFEO、libLEARNA、OmniGenome 等基线比较。
- 我的理解: CocoRNA 通过将长序列分解为多个子问题，每个智能体负责一部分，降低了策略维度；集中式 Critic 利用全局信息指导，缓解了非平稳性；搜索增强探索（SAE）在训练早期提升经验质量，加速收敛。

### 6. 关键发现

- 显著提升成功率: 在相同时间限制下，CocoRNA 达到 97.75% 成功率，比最佳基线高 27.25 个百分点（相对提升 38.7%）。
- 极快设计速度: 平均求解时间仅 3.24 秒，比最佳基线快 70 倍以上。
- 泛化能力: 在 Rfam 数据集上训练，对未见结构也能高效设计，且额外实验表明可扩展到其他生物序列设计任务。

### 10. 对 Agent / Skill / Memory 的启发

- 对 Agent 系统: 展示了多智能体协作在组合优化问题中的潜力，通过分解任务可降低复杂度，集中式训练可提升协作效率。
- 对 Skill: 为生物序列设计提供了一种可扩展的框架，可推广到蛋白质设计、DNA 纳米结构等任务。
- 对 Memory: 集中式 Critic 利用全局状态，相当于共享记忆，有助于协调智能体行为。
- 对评测: 成功率和多样性指标可迁移到其他生成任务，强调精确匹配与多样性平衡。

CocoRNA 是 RNA 逆向设计领域的重要进展，巧妙地将 MARL 应用于组合优化问题。其分解策略和搜索增强探索值得借鉴。未来可探索更智能的分解方法或结合图神经网络处理结构依赖。

## 4. DLite: History-free Speculative Decoding for Agentic AI

**Topics:** Speculative Decoding, LLM Inference Acceleration, Agentic AI
**Authors:** Jiaming Xu, Hanzhen Wang, Tianlang Zhao, Jiewen Xiao, Chengze Yuan, Jiayi Pan, Yongkang Zhou, Jiancai Ye, Yu Wang, Guohao Dai
**Venue / Year:** arXiv 2026
**Links:** [Abstract](http://arxiv.org/abs/2610.23787v1) | [PDF](http://arxiv.org/pdf/2610.23787v1.pdf) | [Code](https://github.com/SJTU-DAI-Sys/DLite)

### 1. 一句话结论

DLite通过直接复用目标模型的隐藏状态，将投机解码从增长历史建模转变为局部预测，在智能体工作负载下实现2到6个token的接受长度，相比DSpark提升最高70%，并完全消除了草稿模型的历史KV缓存维护开销。

### 2. 为什么重要

智能体工作负载（如多轮交互、长上下文）使现有投机解码方法的接受长度下降80%，且草稿模型的历史KV缓存维护占端到端延迟的10%~20%。DLite通过无历史设计同时解决这两个问题，显著提升智能体场景下的LLM推理效率。

### 3. 研究问题

1. 现有投机解码方法在智能体工作负载下性能下降的根本原因是什么？
2. 如何设计一种不依赖历史上下文的草稿模型架构，同时保持高接受长度？
3. 如何有效训练这种与自回归目标模型结构差异显著的无历史草稿模型？

### 4. 背景与问题设定

投机解码通过轻量草稿模型生成候选token并由目标模型验证，以加速LLM推理。然而，智能体工作负载（如SWE-Bench、AgentLongBench）具有长输入、短输出、多轮交互和持续增长的上下文，导致现有草稿模型（如EAGLE、DFlash、DSpark）的接受长度从5~6降至1~2，同时维护草稿模型的历史KV缓存带来显著系统开销。

### 5. 方法概览

- 任务 / 环境: 智能体工作负载（如SWE-Bench、AgentLongBench）以及通用任务（GSM8K、HumanEval等）和长上下文任务。
- 变量 / 干预设计: DLite采用无历史半自回归架构：直接复用目标模型的隐藏状态作为上下文特征，通过可学习的深度嵌入区分来源；使用双向注意力并行生成多个草稿token，并通过轻量级顺序头恢复块内因果依赖。训练采用两阶段策略：先用同构的历史感知教师进行预热，再直接对齐目标模型。
- 评价指标: 接受长度（Acceptance Length）、加速比（Speedup）、端到端延迟。
- 模型比较: 与EAGLE-3、DFlash、DFlash2、DSpark、DFlow等现有投机解码方法对比，在Qwen3-4B和Qwen3-8B上评估。
- 我的理解: DLite的核心创新在于将草稿模型从“独立建模完整历史”转变为“复用目标模型已计算的表示”，从而将问题简化为局部预测。这类似于知识蒸馏中的特征对齐，但更直接地利用了目标模型的中间层输出。

### 6. 关键发现

- 无历史架构显著提升智能体场景接受长度: 在SWE-Bench和AgentLongBench等智能体工作负载上，DLite达到2到6个token的接受长度，相比现有方法（1~2）有显著提升，且相比DSpark提升最高70%。
- 消除草稿模型历史KV缓存维护开销: DLite不维护草稿模型的历史KV缓存，避免了每轮验证后更新和跨轮次前缀缓存的开销，该开销在现有方法中占端到端延迟的10%~20%。
- 两阶段训练策略有效弥合结构差异: 直接使用KL散度对齐目标模型效果不佳，而先通过同构历史感知教师预热再对齐目标模型，训练更稳定且收敛更快。

### 10. 对 Agent / Skill / Memory 的启发

- 对 Agent 系统: DLite可显著降低智能体系统中LLM推理的延迟和资源占用，尤其适合多轮工具调用和长上下文场景，提升整体系统吞吐量。
- 对 Skill: 无历史设计简化了草稿模型的部署，无需维护额外的KV缓存，降低了工程复杂度。
- 对 Memory: 消除了草稿模型的历史KV缓存，减少了内存占用，尤其在长上下文和多轮交互中优势明显。
- 对评测: DLite的接受长度和加速比指标为评估投机解码方法在智能体场景下的有效性提供了新基准。

### 11. 局限性

- DLite依赖目标模型的隐藏状态，因此需要目标模型提供中间层输出，可能增加目标模型的接口复杂度。
- 当前实验仅在Qwen3系列模型上验证，泛化性需进一步测试。
- 无历史设计可能限制对极长上下文的建模能力，尽管实验显示在长上下文任务上表现良好，但极端场景下可能仍有局限。

### 12. 我的看法 / 个人笔记

DLite提出了一种优雅的解决方案，通过复用目标模型表示来避免草稿模型的历史建模负担，思路新颖且实用。两阶段训练策略有效解决了结构差异带来的优化困难。未来工作可探索将无历史思想应用于更多模型架构和任务，并研究如何进一步降低对目标模型隐藏状态的依赖。

### 13. 这篇工作引用的近期高影响力相关文章

  为什么重要：EAGLE系列是自回归草稿模型的代表，通过特征级预测实现高接受长度，但依赖完整历史上下文。
  核心贡献：使用动态特征树和特征级自回归预测，提升草稿质量。

### 14. 总结

DLite是一种针对智能体工作负载的无历史投机解码框架，通过直接复用目标模型的隐藏状态，将草稿预测转化为局部问题，消除了草稿模型的历史KV缓存维护开销，并在多个基准上显著提升接受长度和推理速度。

## 5. Enforcing Code Reasoning in Agentic Scaffold for More Effective Issue Resolution

**Topics:** 软件工程, 编程智能体, 代码推理
**Authors:** Changshu Liu, Ji young Kim, Alireza Ghazanfari, Saanvi Nallu, Reyhaneh Jabbarvand
**Venue / Year:** 2026
**Links:** [Abstract](http://arxiv.org/abs/2610.23782v1) | [PDF](http://arxiv.org/pdf/2610.23782v1.pdf)

### 1. 一句话结论

通过系统化引导代码推理，DeskCheck 在 SWE-bench-Pro 上显著提升了问题解决率，且额外成本极低。

### 2. 为什么重要

当前编程智能体虽常进行代码推理，但多为自发且缺乏引导，导致定位不精确、补丁不完整等问题。DeskCheck 通过强制各阶段代码推理，为提升智能体问题解决能力提供了新思路。

### 3. 研究问题

1. 编程智能体在问题解决轨迹中是否进行代码推理？其形式与频率如何？
2. 代码推理与问题解决成功率有何关联？
3. 如何系统化引导代码推理以提升智能体性能？

### 4. 背景与问题设定

ReAct 式编程智能体依赖推理，但对其代码推理行为缺乏系统研究。现有智能体在问题定位、补丁修复和验证阶段常出现表面化、不完整等问题。

### 5. 方法概览

- 任务 / 环境: SWE-bench-Verified、SWE-bench-Pro、SWE-bench-Lite 基准，涵盖 Python、Go、TypeScript、JavaScript 四种语言。
- 变量 / 干预设计: 提出 DeskCheck 脚手架，在定位、修复、审计、验证阶段强制进行代码推理：模拟执行路径定位根因、模拟候选补丁修复近失补丁、对照需求审计补丁、推理边界输入生成多样化测试。
- 评价指标: 问题解决率、方法级定位召回率、每实例额外成本（美元）、token 使用量。
- 模型比较: 与 mini-SWE-Agent 和 Claude Code 基线对比，使用 MiniMax-M3、GPT-5.6-Luna、Claude Haiku-4.5 作为骨干模型。
- 我的理解: DeskCheck 的核心在于将代码推理显式地融入智能体流程，通过模拟执行和需求审计来弥补自发推理的不足，从而提升问题解决的准确性和完整性。

### 6. 关键发现

- 代码推理普遍存在且与成功率正相关: 在 7,955 条轨迹中，66.95% 包含代码推理，且推理强度与问题解决率正相关，任务越复杂推理越频繁。
- 自发推理存在四大局限: 包括表面化问题复现、测试环境搭建困难、忽略需求细节、验证测试多样性不足。
- DeskCheck 显著提升解决率: 在 SWE-bench-Pro 的 731 个实例上，DeskCheck 比 mini-SWE-Agent 和 Claude Code 分别提高 6.29% 至 10.53%，且额外成本平均仅 0.14 美元。
- 各阶段推理均有贡献: 消融实验显示，逐步加入代码推理使解决率从 53% 单调提升至 68%，证明每个阶段的推理都有效。
