## 1. KaliBench: A Fine-Grained Benchmark for Cybersecurity Tool Use on Kali Linux with Runtime-Free Verifiable Rewards

**Topics:** 网络安全, 命令行工具, 基准测试, 大语言模型
**Authors:** Pengfei Li, Naufal Suryanto, Sicheng Zhang, Muzammal Naseer
**Venue / Year:** arXiv 2026
**Links:** [Abstract](http://arxiv.org/abs/2610.02206v1) | [PDF](http://arxiv.org/pdf/2610.02206v1.pdf) | [Code](https://github.com/RISys-Lab/KaliBench)

### 1. 一句话结论

KaliBench 是一个细粒度基准，用于评估大语言模型将自然语言查询转换为可执行的 Kali Linux 命令的能力，并支持无需运行的验证奖励训练。

### 2. 为什么重要

现有网络安全基准多聚焦知识问答或端到端智能体任务，未直接衡量模型生成可执行命令的能力。KaliBench 填补了这一空白，通过细粒度、可验证的评估，揭示了参数构造是主要瓶颈，并展示了利用该基准进行训练可显著提升模型性能，为网络安全自动化提供了重要工具。

### 3. 研究问题

1. 当前大语言模型能否可靠地将自然语言安全请求转换为精确、可执行的命令行命令？
2. 在无模式（schema-free）的 CLI 场景下，模型在工具选择和参数构造上的表现如何？
3. 基于 KaliBench 的验证奖励训练能否提升模型在网络安全工具调用上的性能？

### 4. 背景与问题设定

大语言模型越来越多地应用于网络安全工作流，需要将分析师的意图转化为工具调用。然而，现有评估要么侧重知识问答，要么侧重端到端智能体任务，未直接衡量模型生成可执行命令的能力。网络安全操作依赖严格的命令行接口，语法错误、标志值绑定错误或参数顺序错误都会导致执行失败。因此，需要一个细粒度、可验证的基准来评估自然语言到 CLI 的翻译能力。

### 5. 方法概览

- 任务 / 环境: Kali Linux 环境，包含 1642 个工具，覆盖 23 个能力维度和 5 个安全阶段。
- 变量 / 干预设计: 评估三种模式：无限制（仅查询）、受限（提供候选工具列表）、提示（提供工具文档）。训练使用监督微调和带验证奖励的强化学习。
- 评价指标: 工具准确率、可选参数 F1（别名感知）、位置参数 F1（多重集匹配）、总分（工具准确率与参数 F1 的均值）、精确正确率（工具和所有参数完全匹配）。
- 模型比较: 评估了 24 种配置的通用和网络安全专用开源模型，包括 8B 模型和 685B MoE 模型。
- 我的理解: 该基准通过分解命令为工具、可选参数和位置参数，实现了细粒度的评估，并利用确定性解析和别名感知评分，确保评估的准确性和可复现性。

### 6. 关键发现

- 无限制模式下模型性能有限: 在无限制模式下，所有评估的开源模型精确命令准确率均未超过 42%，表明准确生成可执行命令仍具挑战性。
- 参数构造是主要瓶颈: 工具选择准确率相对较高，但可选参数和位置参数的 F1 分数较低，说明模型在参数构造方面存在明显不足。
- 训练显著提升性能: 使用 KaliBench 进行监督微调和强化学习后，8B 模型在三种模式下的平均总分提升了 7.5 个百分点，性能接近 685B MoE 模型。

### 10. 对 Agent / Skill / Memory 的启发

- 对 Agent 系统: KaliBench 为网络安全智能体提供了细粒度的评估基准，有助于识别和改进模型在工具调用上的薄弱环节，推动更可靠的自动化安全操作。
- 对 Skill: 该基准强调参数构造的重要性，提示模型需要加强命令语法和参数语义的理解，以提升实际可用性。
- 对 Memory: KaliBench 的验证奖励机制无需运行命令即可提供训练信号，可扩展至需要记忆工具用法的场景，降低训练成本。
- 对评测: 提供了一种可复现、细粒度的评估方法，可推广到其他 CLI 工具领域，促进标准化评估。

### 11. 局限性

- 基准仅覆盖 Kali Linux 工具，可能无法代表所有网络安全工具。
- 评估指标侧重于命令语法和参数匹配，未考虑命令执行后的实际效果。
- 数据生成依赖 LLM，可能存在偏差，尽管经过人工验证。

### 12. 我的看法 / 个人笔记

KaliBench 是一个设计精良的基准，填补了网络安全 CLI 工具调用评估的空白。其细粒度评估和验证奖励机制为模型训练提供了新思路。未来可扩展至更多工具和场景，并考虑命令执行效果，以更全面评估模型能力。

### 14. 总结

KaliBench 是一个针对 Kali Linux 工具调用的细粒度基准，包含 8504 个查询-命令对，覆盖 1642 个工具。通过多阶段验证确保数据质量，并设计了三种评估模式。实验显示开源模型在无限制模式下精确命令准确率低于 42%，参数构造是主要瓶颈。利用该基准进行训练可显著提升 8B 模型性能，接近 685B MoE 模型。

## 2. Mimir: Physics-Grounded LLM Agents for Long-Horizon Irrigation Control

**Topics:** LLM Agent, Irrigation Control, Long-Horizon Control, Physics-Grounded AI
**Authors:** Yimeng Liu, Mi Zhang, Younsuk Dong, Zhichao Cao
**Venue / Year:** arXiv 2026
**Links:** [Abstract](http://arxiv.org/abs/2610.02038v1) | [PDF](http://arxiv.org/pdf/2610.02038v1.pdf)

### 1. 一句话结论

Mimir 通过将 LLM 的语义推理与不可变的数值物理模型和运行时保障分离，实现了长期灌溉控制中的最低成本和约 51% 的节水。

### 2. 为什么重要

该研究展示了 LLM 智能体在长期物理控制任务中的可行架构，强调了在自适应推理与物理安全之间保持明确边界的重要性，为 LLM 在关键基础设施控制中的应用提供了新范式。

### 3. 研究问题

1. 如何将物理状态和约束以结构化方式呈现给 LLM，使其推理基于真实物理量？
2. 如何通过数值模拟验证和修正 LLM 的决策提案，确保执行安全？
3. 如何在不改变物理模型和执行约束的前提下，让智能体从经验中持续改进？

### 4. 背景与问题设定

现有 LLM 智能体多在 episodic 任务中评估，而长期物理控制（如灌溉）要求动作影响未来状态、错误累积且无法重置。灌溉决策需考虑土壤-作物-大气动态，传统方法（如 MPC、RL）在完全指定问题下有效，但 LLM 的引入需解决物理 grounding、决策修复和经验驱动的适应性问题。

### 5. 方法概览

- 任务 / 环境: 灌溉控制：每日决策决定灌溉量，环境包括土壤水分、作物需水、天气等，状态转移由物理模型（水量平衡）决定，目标是最小化累积控制成本（包括灌溉量、水分胁迫、径流和渗漏）。
- 变量 / 干预设计: Mimir 采用双时间尺度架构：快速循环中，LLM 提出灌溉量提案，通过确定性模拟器验证并修订，再由确定性选择器从候选集中选出最优动作，并经过运行时保障和回退路径后执行；慢速循环中，跨季节的重复失败模式被提炼为持久上下文原则，用于影响未来提案，但物理模型、评估器和执行约束保持不变。
- 评价指标: 主要指标为季节物理控制成本 C = w_W W + w_S S + w_R R + w_L L，其中 W 为灌溉量，S 为土壤水分胁迫，R 为径流，L 为深层渗漏，权重固定。
- 模型比较: 对比了历史灌溉重放、MAD-50、ET-Replace、DRLIC（RL 基线）以及消融实验（移除前向模拟、验证修订或持久上下文）。
- 我的理解: Mimir 的核心是分离推理权威和物理权威：LLM 负责生成和修订提案，但最终动作由数值模拟和确定性选择决定，从而在利用 LLM 语义理解的同时保证物理安全。

### 6. 关键发现

- 成本最低且节水显著: 在多个地点、作物和年份的回顾性评估中，Mimir 实现了最低的聚合控制成本（100.94±1.80），且灌溉量比历史重放减少约 51%（2.58±0.12 mm vs 5.32±0.57 mm）。
- 消融实验验证组件必要性: 移除前向模拟、验证修订或持久上下文均导致控制成本上升，表明每个组件都对性能有贡献。
- 模型规模无单调增益: 增大 LLM 规模并未带来一致的性能提升，说明架构设计比模型大小更重要。

### 10. 对 Agent / Skill / Memory 的启发

- 对 Agent 系统: Mimir 提供了一种设计模式：在长期控制任务中，LLM 应作为推理组件而非最终决策者，物理模型和运行时保障必须独立于 LLM。
- 对 Skill: 持久上下文原则可视为一种技能积累，但需确保技能更新不违反物理约束。
- 对 Memory: 记忆机制应区分可变的上下文和不可变的物理规则，避免经验污染物理模型。
- 对评测: 评估应关注长期累积成本而非单步动作，并考虑跨季节的稳定性。

### 11. 局限性

- 仅在灌溉领域验证，其他物理控制任务（如能源、交通）的泛化性未知。
- 依赖准确的物理模拟器，实际部署中模型误差可能影响性能。
- 持久上下文更新可能引入偏差，需要更严格的触发机制。
- 未与最新 LLM 基线（如 GPT-4）对比，模型规模研究有限。

### 12. 我的看法 / 个人笔记

Mimir 是 LLM 智能体在物理控制领域的重要一步，其核心思想——分离推理与物理权威——具有普适性。未来可探索更复杂的物理模型和自适应上下文更新策略，并考虑在真实系统中验证。

### 14. 总结

Mimir 通过双时间尺度架构，将 LLM 的语义推理与数值物理模型和运行时保障结合，在长期灌溉控制中实现了低成本和高节水。其关键设计是快速循环中的提案-验证-修订和慢速循环中的持久上下文更新，同时保持物理模型和执行约束不变。实验表明，Mimir 优于传统方法和消融变体，且模型规模并非关键因素。该工作为 LLM 在长期物理控制中的应用提供了新范式。

## 3. Mem++: Non-Destructive Memory for Long-Term Organizational LLM Agents

**Topics:** LLM Agent, Memory Systems, Organizational Memory, Temporal Reasoning
**Authors:** Ahmad Yehia, Aly O. Abdelkareem, Islam Ahmed, Hesham Omran, Khaled Alashmouny, Christian Claudel, Abduallah Mohamed
**Venue / Year:** arXiv 2026
**Links:** [Abstract](http://arxiv.org/abs/2610.02002v1) | [PDF](http://arxiv.org/pdf/2610.02002v1.pdf) | [Code](https://github.com/AIDAChip-Inc/mem-plus-plus)

### 1. 一句话结论

Mem++ 通过非破坏性存储和读取时选择，在组织记忆基准上显著优于现有记忆系统，同时保持对话场景竞争力。

### 2. 为什么重要

现有记忆系统在写入时压缩或结构化，导致无法回答关于历史版本、矛盾或理由链的问题。Mem++ 提出非破坏性记忆，保留完整文档并在读取时选择，为组织级 LLM 代理提供了更可靠的长期记忆方案。

### 3. 研究问题

1. 如何设计记忆系统以支持组织场景中的时间敏感、矛盾检测和理由链查询？
2. 非破坏性存储与读取时选择相比写入时蒸馏，在组织记忆任务上能带来多少提升？

### 4. 背景与问题设定

组织中的 LLM 代理需要跨文档、跨时间记录决策，但现有记忆系统（如 Mem0、Zep）在写入时压缩或结构化，丢失原始文档和版本信息，导致无法回答关于历史状态、矛盾或理由链的问题。

### 5. 方法概览

- 任务 / 环境: 组织记忆基准 OrgMemBench（443 个文档，157 个线程，18 个月，73 个问题），以及对话基准 LoCoMo 和 LongMemEval-S。
- 变量 / 干预设计: Mem++ 存储每个文档完整文本、日期、作者和嵌入，不调用生成模型。读取时，根据问题日期过滤，融合词法、标签和语义索引的排名，并保留最近文档。可选整合操作标记过时版本。
- 评价指标: LLM 评判分数（主要），F1 和 BLEU-1（对话基准）。
- 模型比较: 与 Full Context、RAG-4096、Mem0、Zep、A-Mem、LangMem、gbrain 等基线比较。
- 我的理解: Mem++ 的核心是延迟决策：不在写入时决定哪些信息重要，而是保留所有原始文档，在读取时根据问题选择相关版本。这避免了信息丢失，但可能增加存储和检索成本。

### 6. 关键发现

- OrgMemBench 上显著优于基线: Mem++ 在 OrgMemBench 上达到 57.6 分（gpt-4.1-mini），比最强基线 RAG 高 2.6 分，比 Mem0 高 20.7 分，比 Zep 高 16.6 分。
- 对话基准上保持竞争力: 在 LoCoMo 和 LongMemEval-S 上，Mem++ 的 LLM 评判分数与最佳基线相当，但 F1 和 BLEU 略低，表明非破坏性存储对对话场景影响不大。
- 整合操作提升性能: 启用整合操作（标记过时版本）后，Mem++ 在 OrgMemBench 上进一步提升，表明版本标记有助于回答时间敏感问题。

- 对 Skill: 非破坏性记忆要求代理具备读取时选择能力，可能促进更复杂的推理技能。
- 对 Memory: 记忆系统应保留原始数据，而非压缩，以支持未知的未来查询。
- 对评测: 需要更多组织记忆基准，以评估时间敏感和矛盾查询。

### 11. 局限性

- OrgMemBench 规模较小（73 个问题），可能不足以全面评估。
- Mem++ 在对话基准上的 F1/BLEU 略低于最佳基线，可能因保留过多无关信息。
- 整合操作依赖阈值，可能不适用于所有场景。

### 12. 我的看法 / 个人笔记

Mem++ 提出了一个简单而有效的思路：不压缩，保留原始，读取时选择。这解决了组织记忆的核心痛点，但可能增加存储和检索成本。未来可探索更智能的读取时选择策略，以及动态整合。

## 4. OmniSeek: Native Tool Integration for Multi-turn Audio-Visual Reasoning

**Topics:** 多模态推理, 智能体, 音频-视觉推理, 工具使用, 强化学习
**Authors:** Haibo Wang, Jiteng Mu, Jialu Li, Jingru Yi, Yuanjun Xiong, Jianming Zhang, Lifu Huang, Mingze Xu
**Venue / Year:** arXiv 2026
**Links:** [Abstract](http://arxiv.org/abs/2610.02181v1) | [PDF](http://arxiv.org/pdf/2610.02181v1.pdf)

### 1. 一句话结论

OmniSeek 通过迭代式工具调用协议，将 Omni-LLM 转变为主动的多轮音频-视觉推理智能体，显著提升了跨模态证据检索与推理能力。

### 2. 为什么重要

现有 Omni-LLM 在处理长音频-视觉序列时，往往被动处理整个输入，导致关键证据被稀释。OmniSeek 提出主动证据获取范式，使模型能够动态决定查看或聆听的模态与时间窗口，为多模态推理提供了新思路，并构建了大规模训练数据与两阶段强化学习策略，具有重要研究价值。

### 3. 研究问题

1. 如何让 Omni-LLM 在长上下文中主动检索跨模态的稀疏关键证据？
2. 如何通过数据合成与强化学习训练模型进行多轮工具调用，避免单模态捷径？

### 4. 背景与问题设定

Omni-LLM 能同时处理文本、音频和视觉输入，但现有模型通常单次编码整个序列，导致长上下文中细粒度视觉细节和短暂音频事件被稀释，模型难以组合跨模态证据，容易依赖语言先验或单模态捷径。现有推理增强方法局限于文本模态，无法动态获取原始音视频证据。

### 5. 方法概览

- 任务 / 环境: 多模态问答任务，输入为视频及其同步音频流，模型需回答需要跨模态证据的复杂问题。
- 变量 / 干预设计: OmniSeek 采用迭代式 思考→工具调用→观察 循环，提供 get_audio_clip 和 get_video_clip 两个工具，分别用于检索指定时间窗口的音频或视频片段。模型自主决定何时调用工具、调用哪个工具以及何时终止循环。
- 评价指标: 主要评估指标为答案准确率（Accuracy），并辅以格式奖励和工具使用奖励。
- 模型比较: 与现有 Omni-LLM（如 Qwen-Omni 系列、MiniCPM-o-4.5）以及基于文本推理的方法（如 OmniVideo-R1）进行比较。
- 我的理解: OmniSeek 的核心创新在于将推理过程显式地外部化为工具调用，使模型能够主动获取原始音视频片段，而非仅依赖全局上下文。通过数据引擎合成高质量轨迹，并用两阶段 RL 优化策略，其中 Audio-Visual Necessity 目标通过注意力掩码奖励真正依赖双模态的轨迹，防止模型走捷径。

### 6. 关键发现

- 主动证据获取提升跨模态推理: OmniSeek 通过迭代工具调用，能够动态定位并检索关键音频和视频片段，显著提高了长上下文中的音频-视觉推理准确率。
- 两阶段强化学习有效优化策略: 在 SFT 冷启动后，使用 GSPO 进行 RL，结合准确性、格式和工具使用奖励，并引入 Audio-Visual Necessity 目标，有效减少了单模态捷径，提升了双模态依赖的推理性能。

## 5. Argo-Bench: Evaluating Data Agents on Enterprise-Scale Workflows

**Topics:** 数据智能体, 企业数据工作流, 文本到SQL, 基准测试, ERP系统, 模拟数据
**Authors:** Gabriel Tomitsuka, Arman Raayatsanati, Emma Xing, Duke Gand, Joseph J Ma
**Venue / Year:** 预印本，审稿中
**Links:** [Abstract](http://arxiv.org/abs/2610.02122v1) | [PDF](http://arxiv.org/pdf/2610.02122v1.pdf) | [Code](https://github.com/TextQLLabs/Argo-Bench)

### 1. 一句话结论

Argo-Bench 是一个包含210个企业级数据科学和分析任务的基准，通过模拟纽约市食品配送平台，生成包含235张表、7.5亿行的Oracle EBS格式数据仓库，并基于行动后果进行评分，超越了传统的文本到SQL基准。

### 2. 为什么重要

现有文本到SQL基准无法反映企业数据工作的复杂性，且存在答案错误率高、数据规模小等问题。Argo-Bench 通过模拟真实业务场景和基于后果的评分，为数据智能体的评估提供了更贴近实际的测试环境，有助于推动该领域的发展。

### 3. 研究问题

1. 如何构建一个能够评估数据智能体在企业级工作流中表现的基准？
2. 当前前沿模型在需要跨表推理、统计分析和行动决策的企业数据任务上表现如何？

### 4. 背景与问题设定

企业数据科学和分析工作流需要跨多表推理、统计分析和行动决策。现有文本到SQL基准仅评估查询生成，且存在答案错误率高、数据规模小、缺乏真实业务场景等问题。由于真实企业数据仓库的敏感性，现有基准多基于公开数据集，无法反映企业级数据工作的复杂性。

### 5. 方法概览

- 任务 / 环境: 模拟纽约市2024年食品配送平台，生成包含235张表、7.5亿行的Oracle EBS格式数据仓库，涵盖订单、配送、支付、财务等模块。数据基于34个公开数据集和报告校准，包括纽约市DCWP季度报告和DoorDash、Grubhub的10-K文件。
- 变量 / 干预设计: 智能体通过Python环境与数据仓库交互，执行SQL查询、运行Python代码，并通过任务控制接口提交行动（如封禁账户、分配预算、发布数据源等）。任务分为五个业务领域：信任与安全、FP&A、市场、会计和增长。
- 评价指标: 根据行动后果评分：封禁列表按避免的欺诈损失计分，预算分配按实现的节省比例计分，预测按加权区间分数计分，数据源和报告按数值准确性计分。
- 模型比较: 评估了14个前沿和开源模型，包括Claude Opus 5.5等，比较它们在210个任务上的表现。
- 我的理解: 该基准通过模拟真实业务场景，将数据智能体的评估从单纯的查询生成扩展到包含决策和行动的全流程，更贴近实际应用。

### 6. 关键发现

- 模型表现普遍不佳: 最强模型Claude Opus 5.5仅在34.8%的任务上得分超过95，平均得分59.5，而9个模型平均得分低于35，表明企业级数据任务对当前模型仍具挑战性。
- 任务类型影响表现: 不同业务领域的任务难度差异显著，预测和预算分配等需要统计建模和优化的任务尤其困难，而简单的查询任务相对容易。
- 参考解决方案验证可行性: 每个任务都有可执行的参考解决方案，证明仅使用数据仓库即可完成任务，但模型往往无法有效探索和利用数据。
